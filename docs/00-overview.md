# votelink2 — 프로젝트 개요

> 상태: 초안 (논의 중) · 최종 수정: 2026-09-01

## 1. 한 줄 정의

공개 데이터를 지속적으로 수집·분석하여, 특정 지역구에 출마한 후보에게
**"언제 / 어디서 / 누구에게 / 무엇을 말할지"** 를 근거와 함께 제시하는 선거 전략 지원 시스템.

## 2. 최종 산출물

시스템이 최종적으로 후보 캠프에 내놓는 것.

| 산출물 | 형태 | 근거가 되는 분석 |
|---|---|---|
| 선거 일정표 | 30분 단위 캘린더 (일자별) | 시간대별 유동인구 × 타깃 세그먼트 접점 × 이동시간 제약 |
| 타깃 전략 | 세그먼트 우선순위 (공략 / 방어 / 설득) | 유권자 프로파일 × 과거 득표 편차 |
| 갭 리포트 | 취약한 지역·계층과 보완 방향 | 위와 동일 (음의 편차 구간) |
| 메시지 자산 | 캐치프레이즈, 현수막 문구, 공보물 목차 | 이슈 지도 × 세그먼트별 언어 |
| 게시물 배치안 | 현수막·벽보 위치 목록 (좌표) | 유동인구 × 법정 허용 위치 |

이 5개가 L3 웹앱의 화면 구성과 1:1로 대응한다.

## 3. 3계층 구조

```
┌─ L1 수집 ─────────────┐   ┌─ L2 분석 ──────────┐   ┌─ L3 표현 ────┐
│ collector × N         │   │ analyzer × N       │   │ 로컬 웹앱     │
│ 뉴스 / 선거결과 /      │──>│ 프로파일링 → 이슈  │──>│ localhost:PORT│
│ 인구통계 / 오픈API /   │   │ → 세그먼트 → 일정  │   │ 대시보드·지도 │
│ 지리 / 여론조사 ...    │   │ → 메시지           │   │              │
└───────────────────────┘   └────────────────────┘   └──────────────┘
      공통 레코드 계약            산출물 JSON 계약
```

**설계 원칙**: L1과 L2는 서로의 코드를 모른다. 오직 `docs/10-data-contract.md`의
공통 레코드 스키마로만 연결된다. 수집기를 늘려도 분석기는 수정되지 않는다.
L2와 L3도 마찬가지로 산출물 JSON 스키마로만 연결된다.

## 4. MVP 경계 (v0.1)

한 번에 다 만들지 않는다. v0.1에서 3계층이 끝까지 한 번 관통하는 것이 목표.

- 대상: **서울 송파구 갑**, 후보 1명
  (선거구에 속한 행정동 목록은 하드코딩하지 않고 선관위 수집기가 데이터로 가져온다)
- 수집기 3종: 과거 선거 결과 / 주민등록 인구통계 / 뉴스
- 분석 2종: 읍면동 단위 유권자 프로파일 / 지역 이슈 랭킹
- 웹앱: 선거구 대시보드·지도 + 선거구 비교(`/compare`) + 전국 동(`/nation`).
  각 화면은 `?election_type=` 으로 대선/총선/지선을 재필터 (대선·총선 데이터 있음, 지선 미수집)
- **v0.2로 미룸**: 일정표 최적화, 메시지 생성, 게시물 배치

## 4-1. 확정된 기술 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 언어 | **Python 단일** (3.11+) | 언어가 하나면 유지보수 시 로드할 컨텍스트가 절반. 수집·분석 생태계도 여기 있다 |
| 패키지 | uv | 재현 가능한 락파일, 빠름 |
| 저장 | 원본 JSONL(불변) + SQLite | DB 서버·Docker 없이 `.db` 파일 하나. 로컬 실행이 목표이므로 |
| 웹 | FastAPI + 서버 렌더 | 별도 프론트 빌드 체인을 두지 않는다 |
| 실행 | `uv run votelink serve` | 한 줄로 포트 열고 웹앱 |
| L2 분석 | **통계·ML + LLM 혼합** | 아래 참조 |

**L2의 "학습"이 의미하는 것 (2트랙)**

- **수치 트랙 (학습함)**: 과거 선거결과 × 인구통계 → 읍면동별 득표율 예측 회귀모델.
  실제로 훈련하고, 선거 후 실측치로 재훈련한다. 산출물은 `.pkl` + 성능지표.
- **텍스트 트랙 (추론함)**: 뉴스·현안 텍스트 → Claude API로 이슈 도출, 세그먼트 언어 분석,
  메시지 초안. 학습이 아니라 매 실행 추론이며, **호출 비용이 발생하는 유일한 지점**이다.

두 트랙은 분리한다. 섞으면 "왜 이런 결론인지"를 설명할 수 없게 되고,
이 프로젝트에서 근거 없는 전략은 실패로 간주한다.

## 5. 확장 방식 — proposal 기반

새 수집기·분석기는 코드가 아니라 **제안서 1장**에서 시작한다.

```
docs/proposals/C-007-naver-news.md  (사람이 작성, 1페이지)
        ↓  skill: new-collector
collectors/naver_news/  스캐폴딩 생성 + registry 등록
        ↓  구현
공통 레코드를 뱉는 수집기 완성
```

제안서 한 장에 담기는 것: 데이터 출처 / 취득 방법 / 갱신 주기 / 공통 레코드로의 매핑 /
법적·기술적 제약. 이 이상은 적지 않는다.

## 6. 지켜야 하는 경계

기능이 아니라 **검증 규칙으로 코드화**할 대상. 상세는 `docs/90-compliance.md`.

- **개인 단위 프로파일링 없음.** 최소 집계 단위는 읍면동. 개인을 식별·추적하는 데이터는 수집하지 않는다.
- **공직선거법 제약을 산출물 검증기로 구현.** 사전선거운동 기간, 현수막 수량·위치 규정,
  선거공보 규격, 여론조사 공표 금지기간, AI 생성물 규제 — 위반 가능성이 있는 산출물은
  웹앱에 경고와 함께 표시하고, 확정 전 캠프의 법률 검토를 전제로 한다.
- **수집은 robots.txt / 이용약관 / 저작권 범위 내.** 뉴스는 원문 전체 저장 대신
  링크 + 메타데이터 + 요약을 원칙으로 한다.
