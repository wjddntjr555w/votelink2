# P-003: 운영자 콘솔

> `P-` = 플랫폼/아키텍처 제안서.
>
> 상태: **부분 채택 · 화면 둘 구현** (2026-09-09). **P-002 를 전제한다** — 인증·역할·감사
> 로그가 없으면 이 문서의 화면은 하나도 성립하지 않는다. P-001 → P-002 → P-003 순서다.
>
> **캠프 관리(§2)와 감사 로그(§5)를 만들었다.** `/ops/` 와 `/ops/audit`, `/ops/camps/<id>`.
> 참조데이터 편집(§3)과 수집·분석 실행(§4)은 아직이다 — §6 이 "화면 넷이 서로 다른 성격이라
> 구현은 나눠서 해도 된다"고 적어둔 그대로 쪼갰다. 남긴 이유는 §2 표에 적었다.

## 1. 무엇을

운영자가 CLI 와 SSH 없이 캠프와 공용 데이터를 관리한다. 화면은 넷이고, 전부 `/ops/*` 아래에
`role='operator'` 로만 열린다.

P-002 가 **차단 요건**이었다면 이건 **운영 편의**다. 없어도 서비스는 돌아간다 — 운영자가 서버에
붙어 CLI 를 치면 된다. 캠프 수가 늘면 그게 병목이 되는 시점에 필요해진다.

## 2. 화면 넷

| 화면 | 무엇 | 상태 |
|---|---|---|
| 캠프 관리 | 승인 큐 · 정지 · 세션 강제 종료 · 비밀번호 재발급 · 캠프 상세 | ✅ `/ops/` · `/ops/camps/<id>` |
| 감사 로그 | 접근 이력 열람 | ✅ `/ops/audit` |
| 참조데이터 편집 | `party_lineage.yaml` 등 | 미구현 — 서버에서 직접 편집 |
| 수집·분석 실행 | 공용 수집기·분석기 실행과 상태 | 미구현 — CLI |

### 왜 둘만 만들었나

**앞의 둘은 P-002 가 이미 만든 것에 화면만 붙인다.** 승인·거절·정지·세션 종료·비밀번호
발급이 전부 `votelink/control/` 에 있고 `votelink account …` 가 같은 함수를 부른다.
새 실패 모드가 없다.

**뒤의 둘은 새 위험을 들여온다.** §6 이 적은 위험 다섯 중 셋이 수집·분석 실행 하나에
몰려 있다 — 웹 프로세스가 `.env` 시크릿을 쥐게 되고, 작업 로그에 API 키가 샐 수 있고,
고아 프로세스 정리가 필요하다. 참조데이터 편집은 서버에 git 작업 트리가 있다는 가정에
걸려 있어서(§6) 배포 형태가 정해지기 전에 만들면 다시 만들게 된다.

**선거 주기 추가는 운영자 화면에 두지 않았다.** 캠프가 `/onboarding` 에서 스스로 채우는
것이 P-002 §6 의 결정이고, 운영자가 대신 입력하면 관할을 캠프보다 운영자가 더 잘 안다는
전제가 된다. 다음 선거 주기를 추가하는 화면은 **캠프 쪽**에 붙었다 — `/cycles`·`/cycles/new`
(2026-09-09, P-001 §7). 운영자는 `/ops/camps/<id>` 에서 결과를 읽기만 한다.

> **P-005 (2026-09-10) 가 이 "읽기만"에 예외 하나를 뒀다** — 캠프가 스스로 못 고치는
> 상태(로그인 불가·정지)거나 이미 저장된 명백한 오류일 때, 운영자가 그 캠프의 주기를
> **대신 교정**한다. 일상 입력이 아니라 교정이고, 캠프가 받는 미리보기·확인을 똑같이
> 거치며, 사유가 감사 로그에 남는다. `docs/proposals/P-005-operator-edits-camp-cycle.md`.

### 승인 화면이 지키는 것

- **`camp_id` 제안값을 보여주고 고칠 수 있게 한다.** 경로가 되는 값이라(`data/camps/<id>/`)
  한 번 정하면 바꾸기 어렵다. 제안값이 이미 쓰이고 있으면 누르기 **전에** 알린다 —
  `kim@a` 와 `kim@b` 가 둘 다 `kim` 을 제안받는 일이 실제로 생긴다.
- **거절은 사유가 없으면 거부한다.** 신청자가 무엇을 고쳐야 하는지 알아야 한다.
- **정지는 세션도 함께 끊는다.** 상태만 바꾸면 남은 세션의 수명만큼 더 열려 있고, 그건
  정지가 아니다.
- **운영자는 자기 계정을 정지할 수 없다.** 운영자가 0명이 되면 아무도 승인할 수 없고
  되돌릴 수도 없다.
- **상태를 바꾸는 것은 전부 POST 다.** GET 으로 두면 링크 한 줄로 남의 캠프가 정지된다.

### 이 화면들에 산출물이 없다

계정·신청·감사 로그는 레코드가 아니다. **운영자 화면에 캠프의 분석 숫자를 올리지 않는다** —
올리는 순간 `verdict` 계산이 필요해지고 절대 규칙 5 가 걸린다. 캠프 상세는 설정과 메타만
낸다(관할 동 **수**, 진영, 선거일, 로스터 이름). 운영에 필요한 것이 그것이다.

### 접근 통제는 라우터가 아니라 미들웨어에 있다

`/ops` 접두어 판정이 `web/auth.py` 에 있다. **P-002 의 `gate` 가 남긴 구멍을 막는 것이다** —
온보딩까지 마친 캠프 계정은 gate 를 통과하고, 그 뒤에는 아무도 막지 않았다. 라우터에
걸지 않은 이유는 `include_router` 를 잊은 다음 사람이 통제까지 함께 잊기 때문이다.
`/d/<선거구>/` 관할 검사와 같은 방식이고 같은 이유다.

## 3. 참조데이터 편집 — 주석을 죽이지 않는 방법

**이 절이 P-003 의 핵심이고, 가장 틀리기 쉬운 지점이다.**

`data/shared/reference/party_lineage.yaml` 은 1032줄인데 **그중 대부분이 데이터가 아니라 판단 근거**다.
민감도 검사 결과, 출구조사 인용과 논문 링크, 동명이인 처리 방식, 왜 3분류가 아니라 4분류인지.
파일이 곧 문서다. `party_lineage.yaml:6` 이 스스로 그렇게 말한다 — "이견이 있으면 이 파일만
고치고 다시 돌린다."

**폼 편집기를 만들면 안 된다.** 진영 값을 드롭다운으로 고르는 화면을 만드는 순간 YAML
라운드트립이 일어나고 주석이 전부 사라진다. 데이터는 남고 **이유가 사라진다.** 그게 이 파일에서
가장 가치 있는 부분이다.

대신:

1. **원문 텍스트 편집.** 편집기는 그냥 `<textarea>` 다.
2. **저장 전 검증** — YAML 파싱 → 스키마 확인 → **기존 로더로 실제 로드**
   (`votelink/reference/party_lineage.py`). 셋 중 하나라도 실패하면 저장을 거부한다.
   검증을 새로 짜지 않고 런타임이 쓰는 로더를 그대로 쓴다 — 그래야 "저장은 됐는데 기동이 안 되는"
   상태가 생기지 않는다.
3. **저장은 git 커밋**으로. 운영자 계정과 사유를 커밋 메시지에 넣는다. 되돌릴 수 있어야 한다.
   `data/shared/reference/` 는 저장소에서 유일하게 git 추적되는 데이터 디렉터리라 이미 그 준비가 되어 있다.

### 저장 전에 영향 범위를 보여준다

P-001 §11 이 예고한 교차 파급이 **여기서 실제로 일어난다**:

> 캠프별 오버라이드를 두지 않기로 했으므로, 진영 분류에 대한 캠프의 이견은 공용
> `party_lineage.yaml` 수정으로만 반영된다. 그 순간 같은 선거구 경쟁 캠프의 숫자도 함께 바뀐다.

그래서 저장 버튼을 누르기 전에 **영향 받는 캠프 수를 보여주고 확인받는다.** 사유는 두 곳에
들어간다 — 감사 로그와, P-001 §11 의 갱신 이력("참조 데이터 변경").

운영자가 자기가 무엇을 흔드는지 모른 채 저장하는 화면을 만들지 않는다.

## 4. 수집·분석 실행 — 첫 백그라운드 작업

지금 웹은 순수 동기 읽기 전용이다. 라우트 7개가 전부 `def` 이고 긴 작업이 하나도 없다.
`votelink collect nec_archive --all-districts` 는 분 단위로 걸린다.

**CLI 를 감싸기만 한다.** `subprocess` 로 기존 명령을 그대로 부르고, 상태는 `jobs` 테이블에,
로그는 파일에 둔다.

```sql
CREATE TABLE jobs (
  id          INTEGER PRIMARY KEY,
  kind        TEXT NOT NULL,        -- 'collect' | 'analyze'
  args        TEXT NOT NULL,        -- JSON. CLI 인자 그대로
  status      TEXT NOT NULL,        -- 'running' | 'done' | 'failed'
  started_at  TEXT NOT NULL,
  finished_at TEXT,
  exit_code   INTEGER,
  log_path    TEXT,
  started_by  INTEGER REFERENCES accounts(id)
);
```

**로직을 이중화하지 않는다.** CLI 가 이미 진실이다 — 격리율 5% 초과 시 커밋 안 함, `--dry-run`,
`--reparse` 같은 규칙이 전부 거기 있다. 웹이 그걸 다시 구현하면 두 개가 갈라진다.

**큐·워커·재시도는 범위 밖이다.** 운영자 1명이 쓰는 화면이고, 동시에 여러 수집을 돌릴 이유가
없다. 같은 수집기가 이미 돌고 있으면 새 실행을 거부하는 정도로 충분하다.

**웹 프로세스가 죽으면 실행 중인 작업은 고아가 된다.** 재시작 시 `status='running'` 인데
프로세스가 없는 행을 `failed` 로 정리한다. 완벽하지 않지만 운영자가 다시 누르면 된다.

## 5. 감사 로그 열람 — 운영자 전용

캠프에게는 열지 않기로 했다.

화면에는 P-002 §7 의 한계를 함께 적는다 — **로그가 "이 캠프의 누군가"까지만 말한다.**
캠프당 계정이 1개라 내부 행위자는 특정되지 않는다. 로그를 읽는 사람이 그걸 모르면
로그를 과신하게 된다.

**제약**: 캠프는 자기 공간의 격리를 스스로 확인할 수단이 없다. 경쟁 캠프를 함께 받는 제품에서
"우리 데이터 아무도 안 봤죠?"는 반드시 나오는 질문이고, 답은 계약과 운영자의 감사 보고다.
이 공백을 문서가 인정하고 지나간다 — 나중에 캠프 열람을 열 여지는 남는다.

## 6. 제약과 위험

- **운영자 계정이 모든 캠프를 볼 수 있다.** 경쟁 캠프를 함께 받는 구조에서 운영자는 단일
  신뢰 지점이다. 기술로 줄일 수 없고 감사 로그로 기록만 된다. 운영자 계정 수를 최소로 유지하는
  것이 유일한 통제다.
- **참조데이터 웹 편집은 서버에 git 작업 트리가 있다고 가정한다.** 컨테이너 배포에서 깨진다.
  깨지면 편집 화면을 비활성화하고 CLI 로 돌아간다(기능 자체를 fail-closed 로).
- **`subprocess` 실행은 웹 프로세스의 권한으로 돈다.** API 키(`.env`)에 접근할 수 있어야 하므로
  웹이 시크릿을 쥐게 된다. P-002 의 `data/control.db` 와 함께 이 프로세스가 침해되면 잃을 것이
  많아진다.
- **작업 로그에 시크릿이 새지 않는지 확인해야 한다.** 수집기가 URL 에 API 키를 붙이면 로그에
  남는다. 저장 전 마스킹이 필요하다.
- **화면 넷이 서로 다른 성격이다.** 승인은 상태 변경, 실행은 프로세스, 편집은 파일, 로그는 조회.
  하나로 묶은 이유는 사용자가 같아서일 뿐이므로, 구현은 나눠서 해도 된다.
