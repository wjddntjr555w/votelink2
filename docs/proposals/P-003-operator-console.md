# P-003: 운영자 콘솔

> `P-` = 플랫폼/아키텍처 제안서.
>
> 상태: **제안** (2026-09-08). **P-002 를 전제한다** — 인증·역할·감사 로그가 없으면 이 문서의
> 화면은 하나도 성립하지 않는다. P-001 → P-002 → P-003 순서다.

## 1. 무엇을

운영자가 CLI 와 SSH 없이 캠프와 공용 데이터를 관리한다. 화면은 넷이고, 전부 `/ops/*` 아래에
`role='operator'` 로만 열린다.

P-002 가 **차단 요건**이었다면 이건 **운영 편의**다. 없어도 서비스는 돌아간다 — 운영자가 서버에
붙어 CLI 를 치면 된다. 캠프 수가 늘면 그게 병목이 되는 시점에 필요해진다.

## 2. 화면 넷

| 화면 | 무엇 | 지금은 |
|---|---|---|
| 캠프 관리 | 승인 큐 · 정지 · 선거 주기 추가 · 세션 강제 종료 | CLI |
| 수집·분석 실행 | 공용 수집기·분석기 실행과 상태 | CLI |
| 참조데이터 편집 | `party_lineage.yaml` 등 | 서버에서 직접 편집 |
| 감사 로그 | 접근 이력 열람 | 없음 |

## 3. 참조데이터 편집 — 주석을 죽이지 않는 방법

**이 절이 P-003 의 핵심이고, 가장 틀리기 쉬운 지점이다.**

`data/reference/party_lineage.yaml` 은 1032줄인데 **그중 대부분이 데이터가 아니라 판단 근거**다.
민감도 검사 결과, 출구조사 인용과 논문 링크, 동명이인 처리 방식, 왜 3분류가 아니라 4분류인지.
파일이 곧 문서다. `party_lineage.yaml:6` 이 스스로 그렇게 말한다 — "이견이 있으면 이 파일만
고치고 다시 돌린다."

**폼 편집기를 만들면 안 된다.** 진영 값을 드롭다운으로 고르는 화면을 만드는 순간 YAML
라운드트립이 일어나고 주석이 전부 사라진다. 데이터는 남고 **이유가 사라진다.** 그게 이 파일에서
가장 가치 있는 부분이다.

대신:

1. **원문 텍스트 편집.** 편집기는 그냥 `<textarea>` 다.
2. **저장 전 검증** — YAML 파싱 → 스키마 확인 → **기존 로더로 실제 로드**
   (`votelink/reference/party_lineage.py`). 셋 중 하나라도 실패하면 저장을 거부한다.
   검증을 새로 짜지 않고 런타임이 쓰는 로더를 그대로 쓴다 — 그래야 "저장은 됐는데 기동이 안 되는"
   상태가 생기지 않는다.
3. **저장은 git 커밋**으로. 운영자 계정과 사유를 커밋 메시지에 넣는다. 되돌릴 수 있어야 한다.
   `data/reference/` 는 저장소에서 유일하게 git 추적되는 데이터 디렉터리라 이미 그 준비가 되어 있다.

### 저장 전에 영향 범위를 보여준다

P-001 §11 이 예고한 교차 파급이 **여기서 실제로 일어난다**:

> 캠프별 오버라이드를 두지 않기로 했으므로, 진영 분류에 대한 캠프의 이견은 공용
> `party_lineage.yaml` 수정으로만 반영된다. 그 순간 같은 선거구 경쟁 캠프의 숫자도 함께 바뀐다.

그래서 저장 버튼을 누르기 전에 **영향 받는 캠프 수를 보여주고 확인받는다.** 사유는 두 곳에
들어간다 — 감사 로그와, P-001 §11 의 갱신 이력("참조 데이터 변경").

운영자가 자기가 무엇을 흔드는지 모른 채 저장하는 화면을 만들지 않는다.

## 4. 수집·분석 실행 — 첫 백그라운드 작업

지금 웹은 순수 동기 읽기 전용이다. 라우트 7개가 전부 `def` 이고 긴 작업이 하나도 없다.
`votelink collect nec_archive --all-districts` 는 분 단위로 걸린다.

**CLI 를 감싸기만 한다.** `subprocess` 로 기존 명령을 그대로 부르고, 상태는 `jobs` 테이블에,
로그는 파일에 둔다.

```sql
CREATE TABLE jobs (
  id          INTEGER PRIMARY KEY,
  kind        TEXT NOT NULL,        -- 'collect' | 'analyze'
  args        TEXT NOT NULL,        -- JSON. CLI 인자 그대로
  status      TEXT NOT NULL,        -- 'running' | 'done' | 'failed'
  started_at  TEXT NOT NULL,
  finished_at TEXT,
  exit_code   INTEGER,
  log_path    TEXT,
  started_by  INTEGER REFERENCES accounts(id)
);
```

**로직을 이중화하지 않는다.** CLI 가 이미 진실이다 — 격리율 5% 초과 시 커밋 안 함, `--dry-run`,
`--reparse` 같은 규칙이 전부 거기 있다. 웹이 그걸 다시 구현하면 두 개가 갈라진다.

**큐·워커·재시도는 범위 밖이다.** 운영자 1명이 쓰는 화면이고, 동시에 여러 수집을 돌릴 이유가
없다. 같은 수집기가 이미 돌고 있으면 새 실행을 거부하는 정도로 충분하다.

**웹 프로세스가 죽으면 실행 중인 작업은 고아가 된다.** 재시작 시 `status='running'` 인데
프로세스가 없는 행을 `failed` 로 정리한다. 완벽하지 않지만 운영자가 다시 누르면 된다.

## 5. 감사 로그 열람 — 운영자 전용

캠프에게는 열지 않기로 했다.

화면에는 P-002 §7 의 한계를 함께 적는다 — **로그가 "이 캠프의 누군가"까지만 말한다.**
캠프당 계정이 1개라 내부 행위자는 특정되지 않는다. 로그를 읽는 사람이 그걸 모르면
로그를 과신하게 된다.

**제약**: 캠프는 자기 공간의 격리를 스스로 확인할 수단이 없다. 경쟁 캠프를 함께 받는 제품에서
"우리 데이터 아무도 안 봤죠?"는 반드시 나오는 질문이고, 답은 계약과 운영자의 감사 보고다.
이 공백을 문서가 인정하고 지나간다 — 나중에 캠프 열람을 열 여지는 남는다.

## 6. 제약과 위험

- **운영자 계정이 모든 캠프를 볼 수 있다.** 경쟁 캠프를 함께 받는 구조에서 운영자는 단일
  신뢰 지점이다. 기술로 줄일 수 없고 감사 로그로 기록만 된다. 운영자 계정 수를 최소로 유지하는
  것이 유일한 통제다.
- **참조데이터 웹 편집은 서버에 git 작업 트리가 있다고 가정한다.** 컨테이너 배포에서 깨진다.
  깨지면 편집 화면을 비활성화하고 CLI 로 돌아간다(기능 자체를 fail-closed 로).
- **`subprocess` 실행은 웹 프로세스의 권한으로 돈다.** API 키(`.env`)에 접근할 수 있어야 하므로
  웹이 시크릿을 쥐게 된다. P-002 의 `data/control.db` 와 함께 이 프로세스가 침해되면 잃을 것이
  많아진다.
- **작업 로그에 시크릿이 새지 않는지 확인해야 한다.** 수집기가 URL 에 API 키를 붙이면 로그에
  남는다. 저장 전 마스킹이 필요하다.
- **화면 넷이 서로 다른 성격이다.** 승인은 상태 변경, 실행은 프로세스, 편집은 파일, 로그는 조회.
  하나로 묶은 이유는 사용자가 같아서일 뿐이므로, 구현은 나눠서 해도 된다.
