> 보류했다가, 사용량이 무료 한도의 0.4% 수준이라 유료 전환 리스크가 낮다고

## 대안 출처 조사 결과 (2026-09-02) — 다시 조사하지 말 것

네이버를 대체할 무료·즉시 출처를 찾았고, **대부분 막혀 있었다.** 결론만 남긴다.

| 후보 | 결과 |
|---|---|
| 공공데이터포털 (기존 `DATA_GO_KR_SERVICE_KEY` 재활용) | ❌ 지역 뉴스 **검색** API가 없다. 언론진흥재단 데이터는 전부 통계 파일 |
| 구글 뉴스 RSS | ❌ `news.google.com/robots.txt` 가 `User-agent: * / Disallow: /`. 규약 §5 위반이라 쓰지 않는다 |
| 송파구청 보도자료 | ❌ robots.txt 가 게시판 URL을 명시적으로 금지 (`/www/selectBbsNttList.do`, `/www/selectBbsNttView.do`) |
| 언론사 개별 RSS | ❌ RSS는 검색이 안 되고 '최신 N건'만 준다. 전국 피드에 지역 필터를 걸면 수확이 거의 0 |
| BIGKINDS | ⚠️ 무료·개인 가능하나 신청→심사→승인 절차. **재개 시 첫 후보** |

> 구글 뉴스 RSS는 기술적으로는 동작했다(실제 송파구 기사 수신 확인). 제목·발행시각·
> 언론사명까지 정확했다. 그러나 robots.txt 전면 금지이고, `description` 에 본문
> 스니펫이 없어 제목만 남으며, 링크가 실제 기사 URL이 아니라 구글 리다이렉트다.
> 세 가지 다 걸린다.

**재개할 때**: BIGKINDS를 C-004로 새로 쓴다. 공통 레코드 계약이 같으므로
아래 매핑과 L2는 그대로 쓸 수 있고, 이 문서의 "왜 필요한가"도 유효하다.

> 실제 호출로 확인하지 못했다 (C-002가 제안 단계의 `access: api` 를

## 무엇을
송파구 관련 뉴스 기사의 **메타데이터와 출처가 준 스니펫**을 가져온다.
제목·언론사·발행시각·URL·요약이 전부다. **본문 전문은 저장하지 않는다.**

검색어는 코드가 아니라 `meta.yaml`의 `queries` 목록이다
(`송파구`, `송파갑`, 9개 행정동명, `잠실`, `올림픽공원`, `가락시장` 등).
검색어를 늘리는 것은 설정 변경이지 코드 변경이 아니다.

## 어디서
- 출처 기관: 네이버 (검색 API) — 원 저작자는 각 언론사
- URL: `https://openapi.naver.com/v1/search/news.json`
- 접근 방식: **api**
- 인증 필요: **있다.** developers.naver.com 에서 애플리케이션 등록 →
  `NAVER_CLIENT_ID` / `NAVER_CLIENT_SECRET`. 무료, 승인 대기 없음.
  헤더 `X-Naver-Client-Id` / `X-Naver-Client-Secret`
- 라이선스: `api_tos` — **`public_open` 이 아니다.** 계약 모델이
  `full_text_stored: true` 를 이 라이선스에서 거부한다(`_check_fulltext_license`).
  전문 저장을 시도하면 코드가 막는다.

**왜 BIGKINDS가 아닌가**: 메타데이터(분류·인물·기관 태그)는 훨씬 풍부하나
API 활용은 별도 신청·승인 절차를 거치고 연구 목적 심사가 붙는다. MVP가
승인 대기에 묶인다. 네이버로 관통시킨 뒤 필요하면 C-00X로 따로 추가한다.

**왜 언론사 RSS·크롤링이 아닌가**: 규약 §5가 "공식 API가 있으면 크롤링하지
않는다"이다. 지역 매체 RSS는 매체마다 형식이 다르고 수집기가 N개로 쪼개진다.

## 왜 필요한가
**L2 텍스트 트랙의 유일한 입력이다.** 이게 없으면 이슈 지도가 만들어지지 않고,
MVP 분석 2종 중 "지역 이슈 랭킹"이 통째로 불가능하다.

직접 쓰이는 곳:
- 갭 리포트 — 어떤 현안이 어느 동에서 반복 언급되는가
- 메시지 자산 — 세그먼트별 언어의 원천 (v0.2)
- 타깃 전략 — 이슈 온도가 높은 동의 우선순위 가중치

## 공통 레코드로의 매핑
- `kind`: `news_article`
- `geo_level`: **`sigungu` 고정.** `geo_code`: `1171000000` (서울 송파구),
  `geo_name`: `서울 송파구`

  > **왜 `emd`가 아닌가.** 기사 하나는 행정동 하나에 속하지 않는다. 기사에
  > `풍납동`이 나왔다고 그 기사를 풍납1동에 귀속시키는 것은 **추정이고, 추정은
  > L1의 일이 아니다**(절대규칙 2). 동 단위 귀속은 L2가 `mentioned_places` 를
  > 근거로 `local_issue` 파생 레코드에서 한다.
  >
  > `1171000000` 은 추정값이 아니다. `mois_population` 이 `lv=3` 조회에
  > 실제로 써서 산하 27개 동을 받아온 코드다
  > (`data/raw/mois_population/2026-09-01/2024-12-1171000000-p001.json.gz`).
  > 그래서 뉴스의 `geo_code` 는 인구·개표결과와 접두사 `11710` 으로 정합한다.
- `observed_at`: `pubDate`(RFC 1123, `Mon, 30 Aug 2026 14:20:00 +0900`).
  `observed_precision`: **`minute`**
- `confidence`: 지역 사전 매칭 강도를 2단으로 넣는다. 이 값은
  "이 기사가 **이 지역구에 대해** 말한다"는 주장의 신뢰도다.
  - `0.9` — 송파갑 9개 행정동명(`districts.yaml`)이 제목·스니펫에 문자열로 존재
  - `0.7` — `송파구` 또는 구 단위 지명만 존재
  기사의 존재 자체는 확실하므로 1.0을 쓰고 싶어지지만, 검색어 매칭 결과를
  1.0으로 두면 L2가 노이즈와 실제 지역 기사를 구분할 근거를 잃는다.
- `natural_key`: **정규화한 기사 URL.** `originallink`가 있으면 그것을,
  비면 `link`를 쓴다. 정규화 = 스킴·호스트 소문자화 + 쿼리스트링·프래그먼트 제거.
  이렇게 하면 **같은 기사가 여러 검색어에 걸려도 `record_id`가 같아 자동으로
  하나가 된다** — 중복 제거 코드를 따로 쓰지 않는다.
- payload(`NewsArticlePayload`):
  - `title`, `url`, `published_at`(원문 표기 보존)
  - `publisher` — **API가 언론사명을 주지 않는다.** `originallink` 호스트에서
    `www.` 를 떼어 넣고, `meta.yaml`의 `publisher_names` 사전에 있으면 그 이름으로
    바꾼다. 사전에 없어도 격리하지 않는다(매체명 미상은 계약 위반이 아니다).
  - `summary` — **LLM 요약이 아니라 API가 준 `description` 스니펫**이다.
    `<b>` 태그와 HTML 엔티티(`&quot;` `&amp;` `&lt;`)만 푼다. 필드명이 `summary`
    라서 오해하기 쉬우니 적어 둔다. 요약 생성은 비용이 드는 L2 텍스트 트랙의 일이다.
  - `full_text_stored`: **항상 `false`**
  - `mentioned_places` — 지역 사전(9개 동명 + `meta.yaml`의 `place_terms`)에
    대한 **완전일치 문자열 매칭 결과만**. 사전 밖 지명은 넣지 않는다(NER은 L2)
  - `mentioned_persons` — `meta.yaml`의 **공인 화이트리스트**(현역 의원·출마 예정자 등)
    에 한한 문자열 매칭. 일반인 이름은 어떤 경우에도 넣지 않는다(절대규칙 3)
  - `topics` — **빈 리스트.** 주제 분류는 해석이고 L2 `local_issue` 의 일이다

**버려지는 것**: 어떤 검색어에 걸렸는지는 payload에 자리가 없어 저장하지 않는다
(`extra="forbid"`). 담으려면 계약 변경이 필요한데, `mentioned_places` 로 대부분
복원되므로 그만한 값이 없다. (C-002가 `기권자수` 를 버린 것과 같은 판단)

**노이즈는 격리가 아니라 필터다.** 제목+스니펫에 지역 사전 항목이 **하나도** 없는
기사는 버린다. `송파`라는 이름의 인물·회사·아파트 브랜드가 검색에 걸리는데,
이건 계약 위반이 아니라 **대상이 아닐 뿐**이다. 격리로 처리하면 격리율이
임계(5%)를 넘겨 수집 전체가 실패한다. (C-002의 관외사전투표 처리와 동일)

## 갱신 주기
- 원 데이터: 상시. 지역 기사는 하루 수십 건 규모
- 수집 주기: `schedule: "0 6 * * *"` (매일 06:00 KST)
- 증분: **`incremental: true`, 단 서버 필터가 아니라 클라이언트 컷오프다.**
  네이버 검색 API에는 기간 파라미터가 없다. `sort=date`로 최신순 페이지를 돌다가
  `since`보다 오래된 `pubDate`가 나오면 그 검색어를 멈춘다(early stop).
  `since=None`이면 `start` 상한까지 전부 받는다.

## 제약과 위험
- 데이터량: 검색어 10개 × 하루 수십 건 → **일 20~80 레코드** 추정.
  레코드가 작아(스니펫 200자) 저장 부담은 없다
- rate limit: 검색 API 일일 **25,000회**. `display=100`, `start` 상한 1000 →
  검색어당 최대 10페이지. 10개 검색어면 하루 100회 미만이라 여유가 크다.
  `rate_limit_rps: 2`
- **`start` 상한 1000이 백필을 막는다.** 검색어당 최대 1,000건까지만 페이징된다.
  과거 기사를 대량으로 소급 수집할 수 없고, 매일 돌려 앞으로 쌓는 수집기다.
  과거가 필요하면 BIGKINDS를 별도 수집기로 붙이는 수밖에 없다
- **`pubDate`가 미래인 기사가 존재한다**(발행 예약, 매체 시각 오류). 계약이
  `observed_at > ingested_at` 을 거부하므로 그대로 두면 격리된다. 격리가 정답이며
  시각을 손보지 않는다 — 다만 격리 사유 상위에 이게 뜨면 원인을 본다
- `originallink`가 빈 문자열인 경우가 있다. 이때 `link`(네이버 뉴스 URL)를 쓰면
  `publisher`가 `n.news.naver.com` 이 된다. 틀린 게 아니라 **모르는 것**이므로
  그대로 두고 `publisher_names` 사전으로 나중에 덮는다
- 같은 사건을 여러 매체가 쓴 기사는 URL이 달라 **각각 별도 레코드로 남는다.**
  이건 중복이 아니라 언급량 신호이므로 L1에서 합치지 않는다
- 출처 형식 변경 위험: 낮다. 네이버 검색 API는 장기간 안정적이다.
  다만 `description` 스니펫 길이·태그 규칙은 예고 없이 바뀔 수 있어
  `summary` 는 계약 상한(600자)에서 자른다
- **법적 검토**:
  - 저작권 — 링크 + 메타 + 출처 스니펫까지만 저장한다. 규약 §5와 계약 모델이
    이중으로 강제한다. 웹앱에서도 원문 링크로만 연결하고 스니펫 이상을 재현하지 않는다
  - 공직선거법 — 여론조사 결과를 인용한 기사가 섞여 들어온다. **공표금지기간
    (선거일 6일 전~투표 마감)** 에 이걸 재가공해 표시하면 위반 소지가 있다.
    수집은 문제없고, **웹앱 표시 단계의 검증 규칙**으로 다룬다
    (`docs/90-compliance.md` — 아직 미작성)
  - 네이버 API 이용약관 — 수집한 결과를 제3자에게 재배포하지 않는다.
    로컬 웹앱 단독 사용이라 현재 범위 안이다
