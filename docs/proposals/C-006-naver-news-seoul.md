# C-006: naver_news — 서울 25개 자치구로 확장

> `C-` 자리에 두지만 새 수집기가 아니다. 기존 `naver_news` 의 `config.districts`
> 를 넓히는 **설정 확장** 제안서다. 코드·스키마 변경 없음. 표가 길어 1페이지를
> 넘지만, 내용은 자치구 24행의 검색어 사전 하나뿐이다.

> 상태: **제안**. D-001 후속(§후속에 명시된 "다지역구 지원의 나머지 반") 중
> `naver_news` 몫.

## 무엇을

`collectors/naver_news/meta.yaml` 의 `config.districts` 를 `seoul_songpa_gap`
1개 → 서울 25개 자치구로 확장한다. 자치구당 블록 1개, 블록 키는 그 자치구를
담는 **대표 선거구 id**(대개 `_gap`). 수집을 자치구마다 한 번씩 돌리면
`data/records/naver_news.jsonl` 에 서울 전역 기사 메타가 쌓인다.

## 왜 필요한가

`districts.yaml` 는 D-001 로 서울 48개 선거구가 완비됐고 웹앱 `/` 선거구
선택·`/d/<선거구>/news` 도 이미 범용이다. 그런데 `naver_news` 가 송파구 갑
하나만 알아서, 다른 47개 선거구는 뉴스 탭이 빈 채로 뜬다. 이 확장이 그
빈자리를 채운다 — 최종 산출물 중 **갭 리포트·메시지**의 "이 동네가 지금 뭘
걱정하나" 재료.

## 집계 단위 = 자치구 (선거구 아님)

뉴스 레코드는 `geo_level: sigungu`, `geo_code` = 자치구 코드다
(`collector.py:155-159` — 기사 하나를 행정동에 귀속시키는 건 추정, L1 이 안
한다). 웹 `load_news` 도 선거구의 행정동 코드에서 **시군구 프리픽스 집합**을
만들어 필터한다(`votelink/web/loader.py:325-339`). 따라서:

- 자치구당 블록 1개면 충분하다. 같은 자치구의 갑/을/병 화면은 **같은 뉴스
  목록**을 본다 — 의도된 결과(사용자 결정 2026-09-06).
- 블록 키는 선거구 id 여야 한다(`votelink/districtcfg.py` 가 그 키로
  `resolve_config`). 그래서 "자치구 별칭 키"는 불가 — 대표 선거구 id 를 쓰되
  같은 자치구의 다른 선거구로 `--district` 를 줘도 동작하도록, 필요하면 그
  선거구 id 도 같은 `sigungu_code` 로 블록을 복제할 수 있다(이번 범위는
  대표 1개만).

## 검색어 사전 (검수 대상)

`sigungu_code` 는 `collectors/mois_population/meta.yaml:70-172` 에서 그대로
복사. `queries[].id` 는 ascii(raw 파일명), `q` 는 실제 검색어. `sigungu_terms`
중 하나도 기사에 안 걸리고 `district_terms`·행정동명에도 안 걸리면 그 기사는
버려진다(`collector.py:133,181-187`) — 그러니 자치구명 변형을 반드시 넣는다.
`districts.yaml` 의 행정동명(예 "역삼1동")은 코드가 자동 병합하므로
`district_terms` 에는 **법정동·통칭·랜드마크**만 적는다.

## 실행

한 번의 `collect` 는 선거구 하나만 받으므로, 25개 블록을 한 줄로 돌리는
`--all-districts` 플래그를 `votelink/cli.py` 에 신설했다 (C-006 동반 변경):

```bash
uv run votelink collect naver_news --all-districts --dry-run   # 설정·계약 검증
uv run votelink collect naver_news --all-districts             # 실제 수집
```

meta 의 `config.districts` 키를 전부 순회하며 선거구마다 새 인스턴스로
`runner.run` 을 호출하고, 선거구별 리포트 + 마지막에 합산 요약을 낸다. 한
선거구가 `FetchError` 로 실패해도 나머지는 계속 돈다. `analyze` 에도 같은
플래그가 붙는다.

## 갱신 주기

`meta.yaml` 의 `schedule: "0 6 * * *"`·`incremental: true` 를 그대로 쓴다.
자치구별 실행은 위 `--all-districts` 한 줄.

## 제약과 위험

- **예상량**: 첫 백필 ≈ 24 자치구 × ~7 검색어 × ≤10페이지 ≈ 1,700 호출·수만 건.
  일일 증분 ≈ 24 × ~7 × 1~2페이지 ≈ 300 호출. NAVER 검색 API 한도 25,000/일
  대비 여유.
- **노이즈**: 자치구명·랜드마크 검색이라 스포츠·행사·부동산·인물 동명이인이
  섞인다. 계약 위반이 아니라 대상 판별이 L2(`issue_ranker`)의 일이다
  (C-003 과 동일). 이번 범위는 L1 데이터만 — 분석기는 확장하지 않는다.
- **중구·성동구 을 특례**: `seoul_jung_seongdong_eul` 의 emd 는 중구 15동 +
  성동구 4동(금호1~4가동·옥수동)이 섞여 있다. `naver_news` 는 `sigungu_code`
  하나만 받으므로 이 블록은 중구 코드(`1114000000`)로 두고, 성동구 뉴스는
  `seoul_jung_seongdong_gap` 블록(`1120000000`)이 담당한다. 두 선거구 화면
  모두 emd 코드 전체에서 시군구 프리픽스 집합(`{1114…, 1120…}`)을 만들어
  양쪽 뉴스를 읽으므로 표시에는 문제 없다.
- **형식 변경 위험**: C-003 이 이미 감수한 NAVER API HUB 이관 리스크 그대로.
  자치구 확장이 새로 만드는 위험은 없다.
- **법적 검토**: 새 kind 없음. `news_article` 은 `compliance.yaml` 에 이미
  등록(`risk: low`, `distribution: internal_only`, `status: unreviewed`).
  여론조사 인용 기사의 공표금지기간 배너(`election_day: null` → `unreviewed`)
  는 자치구 수와 무관하게 기존 동작.

## 이번 범위 아님

- 선거구(갑/을/병) 단위 뉴스 분리 — 웹 loader/viewmodel·분석기 집계 로직
  변경이 필요하다. 자치구 단위로 충분하다는 결정에 따라 보류.
- `news_pulse`·`issue_ranker` 의 `districts:` 확장 및 `issue_lexicon.yaml`
  서울 전역화.
- 선거구별 공인(현역·예비후보) 명단으로 `person_terms` 채우기.
