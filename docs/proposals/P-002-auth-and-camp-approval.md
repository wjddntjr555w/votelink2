# P-002: 인증 · 캠프 승인 · 세션

> `P-` = 플랫폼/아키텍처 제안서. 1페이지 원칙의 예외다(P-001 과 같은 이유).
>
> 상태: **채택 · 구현 완료** (2026-09-08). **P-001 에 의존한다** — P-001 이 바뀌면 이 문서도 바뀐다.
>
> §13 롤아웃 1~7단계 전부 끝났다. `uv run votelink account create-operator` 로 운영자를 만들고
> `uv run votelink serve --auth` 로 띄우면 가입 → 승인 → 온보딩 → 캠프 화면이 돈다.
> 구현하며 이 문서를 세 곳 고쳤다: §9 `/pending` 등급, §10 구멍을 막는 방식, §5 감사 로그의 외래키.
>
> P-001 §16 이 "**인증·감사 로그 없이는 운영할 수 없다. 그때까지 멀티캠프 모드는 기동을
> 거부한다**"고 적었다. 이 문서는 편의 기능이 아니라 **P-001 을 실제로 쓰기 위한 차단 요건**이다.

## 1. 무엇을

후보 캠프의 가입·운영자 승인·로그인·세션을 붙인다. 그래서 P-001 이 정의한 캠프 데이터 격리를
**실제로 집행 가능하게** 만든다.

지금 `votelink/web/` 에는 인증 관련 코드가 **정확히 0줄**이다. 미들웨어 0개, POST 라우트 0개,
쿠키·세션 전무. 라우트 7개가 전부 동기 읽기 전용이다. 바닥부터 만든다.

## 2. 전제의 변경 — 비노출이 인증이었다

`votelink/web/__init__.py:12-17` 이 기본 호스트를 못박아 두었다:

> `DEFAULT_HOST = "127.0.0.1"` — 편의가 아니라 컴플라이언스에 인접한 결정이다. 미검토 산출물이
> 경고와 함께 뜨는 화면을 LAN 에 열어두면 그게 의도치 않은 공표가 된다(`docs/90-compliance.md §6`).

즉 **지금은 "네트워크에 노출하지 않는다"가 곧 인증 대체물**이다. 호스팅은 이 전제를 폐기한다.
**P-001 §18 의 폐기 목록에 빠져 있던 항목이다** — 이 문서가 메운다.

### 무엇이 대체하는가 — 공개 표면이 비어 있다

인터넷에 열리는 화면은 다섯 개뿐이고, **그중 어디에도 산출물이 없다**:

```
/login  /signup  /pending  /healthz  /static/*
```

그래서 `0.0.0.0` 바인딩이 "의도치 않은 공표"가 되지 않는다 — 공표할 내용 자체가 공개 표면에
없기 때문이다. 산출물이 붙은 화면은 전부 로그인 뒤에 있다(§9).

**인증이 꺼져 있으면 `0.0.0.0` 바인딩을 거부한다.** 근거가 사라진 채로 열리는 경로를 남기지
않는다. 기존 fail-closed 선례(`cli.py:461-467`)와 같은 형태 — 트레이스백 없이 한국어 한 줄 +
stderr + `return 1`.

### 강해지는 전제도 있다

`templates/base.html:1-2` 는 다른 이유를 댄다:

> 외부 요청 0건이어야 **캠프의 열람 맥락이 제3자에게 새지 않는다.**

이건 폐기 대상이 아니라 **더 중요해진다.** 경쟁 캠프를 한 서버에 받기로 했으므로(P-001 §10),
"누가 무엇을 들여다보는지"가 새면 안 될 이유가 하나 더 생긴다. 외부 요청 0건 규칙과 그것을
지키는 테스트(`tests/test_web.py:212-220`)는 그대로 간다.

## 3. `L3 는 쓰지 않는다` — 규칙을 벼린다

`votelink/web/__init__.py:3-5` 가 L3 의 쓰기를 금지하고 `store.append_records` 를 import 하는
것조차 막는다. **그런데 로그인은 본질적으로 쓰기다.**

규칙을 없애지 않는다. **문구를 벼린다:**

> ~~L3 는 쓰지 않는다~~ → **L3 는 레코드를 쓰지 않는다.**

지키려던 불변식은 "서빙이 분석 코퍼스를 변형하지 않는다"였고, 그건 그대로다. 계정·세션·감사는
`data/records/` 밖의 **별도 저장소**(§4)다.

증거가 이미 있다: `tests/test_web.py:239-258` `test_serving_never_writes` 는 `records_root`
하위만 감시한다. **이 테스트는 수정 없이 계속 통과해야 하며, 통과한다는 사실이 곧 규칙이
지켜졌다는 증거다.** 통과시키려고 테스트를 고치는 순간 규칙이 사라진다.

## 4. SQLite — 트리거가 앞당겨졌다

`docs/11-storage.md:100-112` 는 SQLite 도입 시점을 "건수가 자릿수로 커질 때"로 적어뒀다
(`foot_traffic` 같은 kind 가 들어와 JSONL 전량 로드가 무너질 때). 인증은 **양이 아니라
동시성**으로 그 시점을 앞당긴다 — 동시 로그인·세션 갱신은 파일 락으로 감당할 일이 아니다.

도입하되 **구분을 세운다:**

| | 무엇 | 어디 |
|---|---|---|
| **control plane** | 계정·세션·승인 신청·감사 로그 | `data/control.db` (신규) |
| **data plane** | 분석 코퍼스 | `data/shared/records/*.jsonl` (P-001) — **안 옮긴다** |

`docs/00-overview.md:58` 이 예고한 `data/votelink.db` 라는 이름을 쓰지 않는다. 그 이름은
레코드 질의 계층 몫으로 남겨둔다. 두 가지는 목적도 수명도 다르다.

stdlib `sqlite3` 이므로 **의존성이 늘지 않는다.**

## 5. 스키마

```sql
CREATE TABLE accounts (
  id            INTEGER PRIMARY KEY,
  email         TEXT NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,          -- hashlib.scrypt, 파라미터를 문자열에 함께 담는다
  role          TEXT NOT NULL,          -- 'camp' | 'operator'
  camp_id       TEXT,                   -- role='camp' 일 때만. P-001 의 디스크 캠프를 참조
  status        TEXT NOT NULL,          -- 'pending' | 'active' | 'suspended'
  created_at    TEXT NOT NULL,
  last_login_at TEXT
);

CREATE TABLE signup_requests (
  id           INTEGER PRIMARY KEY,
  account_id   INTEGER NOT NULL REFERENCES accounts(id),
  candidate_name TEXT NOT NULL,
  contact      TEXT NOT NULL,
  wanted_election TEXT,                 -- 희망 선거. 자유 기술. 승인 판단용일 뿐
  status       TEXT NOT NULL,           -- 'pending' | 'approved' | 'rejected'
  requested_at TEXT NOT NULL,
  decided_at   TEXT,
  decided_by   INTEGER REFERENCES accounts(id),
  note         TEXT                     -- 운영자의 판단 근거. 거절 사유
);

CREATE TABLE sessions (
  token_hash TEXT PRIMARY KEY,          -- 원문 토큰은 저장하지 않는다
  account_id INTEGER NOT NULL REFERENCES accounts(id),
  created_at TEXT NOT NULL,
  expires_at TEXT NOT NULL,
  ip         TEXT,
  user_agent TEXT
);

CREATE TABLE audit_log (
  id         INTEGER PRIMARY KEY,
  at         TEXT NOT NULL,
  account_id INTEGER REFERENCES accounts(id),
  camp_id    TEXT,                      -- 어느 캠프 공간에 대한 행위였나
  action     TEXT NOT NULL,             -- 'login' | 'view_district' | 'approve_camp' | ...
  target     TEXT,
  detail     TEXT,                      -- JSON
  ip         TEXT
);
```

**캠프 설정은 DB 에 넣지 않는다.** P-001 의 `camps/<camp_id>/camp.yaml` 이 그대로 진실이고,
DB 는 `camp_id` 를 문자열로 참조만 한다. 진실의 출처를 둘로 만들면 어느 쪽이 맞는지를 두고
싸우게 된다 — `districts.yaml` 과 `meta.yaml config.districts` 가 이미 수동 동기화로 겪는 일이다.

## 6. 가입 → 승인 → 온보딩 — 2단계

**이 절이 P-001 §17 을 철회한다.** P-001 은 "웹 온보딩 폼은 이번 범위 아님, CLI 가 먼저"라고
적었으나, 웹 가입이 생기면 성립하지 않는다 — 가입 신청 폼이 곧 온보딩이 되기 때문이다.

대신 **둘로 나눈다.** 영업 문턱을 낮추면서 정확한 온보딩을 받는 방법이다.

| 단계 | 받는 것 | 만들어지는 것 |
|---|---|---|
| **신청** | 이름·연락처·희망 선거 정도 | `signup_requests` 행 + `status='pending'` 계정 |
| **승인** | 운영자의 판단(계약·신원 확인은 시스템 밖) | `camps/<camp_id>/camp.yaml` **골격만** |
| **온보딩** | 관할 emd·진영·선거일·상대 로스터 (P-001 §6 의 항목 전부) | `cycles/<id>/election.yaml` · `candidates.yaml` |

**승인이 DB↔디스크 인계점이다.** 승인 전에는 캠프 공간이 존재하지 않는다.

**온보딩 미완료 캠프는 데이터 화면에 접근할 수 없다.** 관할이 없으면 무엇을 보여줄지 알 수
없으므로 fail-closed 가 자연스럽다 — 조용히 전국을 보여주거나 빈 화면을 주지 않는다.

**emd 코드 검증을 여기에 넣는다.** P-001 §16 이 "관할 입력이 틀리면 모든 분석이 조용히 틀린다"를
가장 위험한 실패 방식으로 지목했다. 온보딩 저장 시 `districts.yaml` 대조로 코드 존재·중복을
확인하고, 실패하면 저장을 거부한다.

**미승인 계정은 `/pending` 만 본다.** 공용 데이터도 보이지 않는다 — §2 의 근거("공개 표면에
산출물이 없다")를 지키려면 승인 전 계정에게도 열 수 없다.

## 7. 캠프당 계정 1개가 뜻하는 것

캠프 = 계정 1개를 캠프원끼리 공유한다. 가장 단순하고 빨리 만들어진다. 대가를 정직하게 적는다.

**감사 로그는 "이 캠프의 누군가"까지만 말한다.** 캠프 *간* 유출은 추적되지만 캠프 *내부*
행위자는 특정되지 않는다. 경쟁 캠프를 함께 받는 제품에서 추적이 필요한 것은 캠프 간 경계이므로
이 한계를 감수한다.

**시스템은 법률 검토 서명을 보증하지 않는다.** P-001 이 `compliance.review.yaml` 의
`reviewed_by` 를 실명 서명으로 설계했지만, 공유 계정으로는 그 이름이 그 사람인지 확인할 수 없다.

충돌은 아니다 — `compliance.yaml:11-13` 은 이미 `reviewed_by` 를 **사람이 손으로 적는 자유
문자열**로 두고 있고, "서명 없는 서명란은 서명이 아니다"까지만 검사한다. 시스템은
"이 캠프 계정이 이 이름을 적었다"를 기록할 뿐이다. `base.html:53-54` 의 푸터가 이미 같은 말을
한다 — "최종 판단자는 캠프의 법률 검토다."

## 8. 인증을 무엇이 강제하는가

### 비밀번호와 세션

- **비밀번호**: stdlib `hashlib.scrypt`. 외부 라이브러리를 쓰지 않는다 — `pyproject.toml:12-14`
  가 "uvloop 는 Windows 에서 안 깔린다"며 순수 휠을 선호하는 기조를 이미 적어두었다.
- **세션**: `secrets.token_urlsafe` 로 만든 토큰을 쿠키에, **해시**를 DB 에 둔다. 원문은 저장하지
  않는다. 조회로 검증하므로 서명 쿠키가 필요 없고 **`itsdangerous` 의존성이 사라진다.**
- **만료**: 유휴 12시간(요청마다 연장). 캠프는 하루 종일 쓰는 도구라 짧으면 방해가 된다.
- **2FA 를 두지 않는다.** 공유 계정에서는 시드도 함께 공유되어 방어력이 절반으로 떨어진다.
  대신 세션을 DB 에 둔 덕에 **강제 종료가 공짜로 따라온다** — 운영자가 의심스러운 세션을 즉시
  끊을 수 있다. 접속 IP·시각은 `audit_log` 에 남는다.

### 집행은 미들웨어로

예외 핸들러는 라우트가 검사를 *호출해야* 동작한다. 즉 **빠뜨릴 수 있다.** 새 라우트를 추가하며
검사를 잊으면 조용히 열린다. P-001 §10 이 "빠뜨리면 `TypeError`"를 고른 것과 같은 이유로,
여기서도 **못 빠뜨리는 쪽**을 고른다.

`create_app` 은 지금 미들웨어가 0개다(`app.py:60-71`). 세션 해석과 접근 판정을 첫 미들웨어로
넣고 결과를 `request.state.account` 에 심는다. `app.state` 는 앱 전역이라 요청별 사용자를
담을 수 없다 — `request.state` 는 현재 미사용이라 비어 있다.

`app.py:8` 이 `Depends()` 를 안 쓰기로 한 결정("라우트는 `request.app.state` 를 읽는다")과
충돌하지 않는다. 라우트별 의존성 주입과 앱 전역 미들웨어는 별개 사안이다.

### 리다이렉트는 기존 패턴으로

`NotAuthenticated` 예외를 만들고 `/login` 302 핸들러를 붙인다. `app.py:170-171` 이 예외 핸들러를
루프로 등록하는 패턴을 이미 갖고 있어 그대로 확장된다.

### `_ctx` 와 `error.html`

로그인 상태는 `_ctx()`(`app.py:189`)에 한 줄 넣으면 전 템플릿에서 쓸 수 있다 — 모든 화면이
통과하는 단일 조립점이기 때문이다.

**단 `error.html` 은 여기를 비껴간다.** `_setup_error`(`app.py:204-210`)가 `_render` 를 쓰지 않고
templates 를 직접 호출한다. 그대로 두면 에러 화면에서만 로그인 상태가 사라진다. 같이 고친다.

### 템플릿

`base.html:47` 의 `로컬 전용 · 캠프 내부 열람` 을 로그인 상태·로그아웃으로 바꾼다.
이 문구는 §2 에서 폐기한 전제를 화면에 그대로 적어둔 것이라 어차피 틀린 말이 된다.

## 9. 라우트 지도

| 등급 | 경로 | 조건 |
|---|---|---|
| **공개** | `/login` · `/signup` · `/healthz` · `/static/*` | **산출물 없음** |
| **대기** | `/pending` · `/logout` | 로그인만 되어 있으면 (승인 전 포함) |
| **캠프** | `/onboarding` | 승인됨 |
| **캠프** | `/` · `/d/{id}/` · `/d/{id}/map` · `/d/{id}/news` · `/compare` · `/nation` | 승인 + 온보딩 완료 |
| **운영자** | `/ops/*` | role='operator' (화면은 P-003) |

> **구현하며 고친 것:** 초안은 `/pending` 을 공개 등급에 뒀다. 실제로 만들어 보니 틀렸다 —
> 그 화면은 *내 신청이 어떤 상태인가*를 말하므로 세션이 없으면 보여줄 것 자체가 없고, 세션
> 없이 열어두면 남의 신청 상태를 물어볼 수 있는 표면만 생긴다. 대기 등급으로 내렸다.
> `/logout` 은 지도에 없었는데, 승인 대기·온보딩 중인 계정도 나갈 수 있어야 해서 같은
> 등급에 둔다. **`/logout` 은 POST 만 받는다** — GET 이면 남의 페이지에 심은 이미지 한 장으로
> 세션이 끊긴다.

`/compare`·`/nation` 은 공용 데이터지만(P-001 §4 — 공용 코퍼스는 전 캠프 읽기 전용)
**로그인 뒤로 넣는다.** 접근 권한의 문제가 아니라 §2 의 근거를 지키는 문제다 — 미검토 산출물이
붙은 화면은 공개 표면에 둘 수 없다.

캠프 화면은 **세션의 `camp_id` 로 스코프된다.** URL 의 `district_id` 가 그 캠프의 관할
(`election.yaml` 의 `emd_codes`)에 속하지 않으면 거부한다. P-001 §10 의 저장 계층 격리에
대응하는 웹 계층 짝이다.

**이 검사도 미들웨어에 있다.** 라우트마다 부르게 두면 `/d/` 밑에 화면을 하나 더 붙일 때
빠뜨릴 수 있어서, 경로 모양(`/d/<id>/…`)으로 판정한다 (`web/auth.py:district_in_path`).
겹치기만 하면 통과시킨다 — 캠프 관할과 국회의원 선거구는 서로 포함 관계가 아니다.
구청장 캠프의 관할은 선거구 셋에 걸쳐 있고 기초의원 캠프는 한 선거구의 일부만 갖는다
(P-001 §6). 교집합이 비었을 때만 남의 지역구다.

**모르는 선거구는 여기서 막지 않는다.** 라우트가 `DistrictNotFound` 로 처리한다 —
"없는 선거구"와 "남의 선거구"를 같은 화면으로 뭉개면 어느 쪽인지 알 수 없다.
거부는 403 이지 로그인 리다이렉트가 아니다. 다시 로그인해도 달라지지 않는 일에 로그인
화면을 보여주면 거짓말이 된다. 거부한 순간은 `audit_log` 에 `denied` 로 남는다 — 경쟁
캠프를 함께 받는 제품에서 "유출이 없었다"를 증명할 수단이 그것뿐이다.

## 10. 절대 규칙 5 의 구멍을 막는다

`templates/_output.html:12-13` 에 구멍이 있다:

```jinja
{% if verdict is none %}
  {{ caller() }}          {# 경고 없이 렌더된다 #}
{% else %}
```

같은 파일 상단 주석은 이렇게 적혀 있다 — "**경고 없이 콘텐츠만 그릴 수 있는 경로가 존재하지
않는다.**" 문면과 어긋난다.

지금까지는 드러나지 않았다. 화면이 7개뿐이고 전부 verdict 를 계산해 넘기기 때문이다. 그러나
로그인 뒤에 새 화면(온보딩·운영자 콘솔·캠프 대시보드)을 붙이기 시작하면, verdict 를 계산하지
않고 `None` 을 넘기는 순간 **조용히 규칙 5를 우회한다.**

`verdict is none` 분기를 제거한다. 회귀 테스트를 붙인다.

> **구현하며 고친 것:** 초안은 "verdict 없이 부르면 Jinja 가 터진다"로 적었다. 만들면서
> 그게 두 가지 이유로 틀렸다는 걸 알았다.
>
> 첫째, **`None` 이 정당하게 오는 경로가 이미 있다.** `worst_verdict([])` 가 `None` 을
> 돌려주고, `compare.html` 은 행이 있는데 각 행의 판정이 전부 없는 경우에 그것을 받는다.
> 터뜨리면 그 화면이 통째로 500 이 된다.
>
> 둘째, 터지는 것이 더 안전하지도 않다. 필요한 성질은 *수치가 HTML 에 나가지 않는다*이지
> *예외가 난다*가 아니다.
>
> 그래서 **판정 없음을 `blocked` 와 같게 다룬다** — `caller()` 를 부르지 않고 "검증 판정이
> 없어 표시하지 않는다" 배너만 그린다. 판정 없음은 "안전"이 아니라 "모름"이라는 뜻이고,
> 모르면 안 그리는 것이 fail-closed 다. 규칙은 이제 호출자가 아니라 매크로에 있다.
> `tests/test_web.py::test_the_output_macro_refuses_a_missing_verdict` 가 이것을 잠근다.

## 11. 새 의존성

**`python-multipart` 하나뿐이다.** FastAPI 의 폼 POST 에 필수고, 이 앱 최초의 POST 라우트가
로그인이다.

| 안 쓰는 것 | 이유 |
|---|---|
| `itsdangerous` | 세션을 DB 에 두므로 서명 쿠키가 불필요 (§8) |
| `passlib` · `bcrypt` · `argon2-cffi` | stdlib `hashlib.scrypt` 로 충분 |
| `pyotp` | 2FA 를 두지 않음 (§8) |
| `sqlalchemy` | stdlib `sqlite3`. 테이블 4개에 ORM 을 들이지 않는다 |

`dependencies` 에 넣는다. `[dependency-groups]` 와 섞지 않는다 — `pyproject.toml:22-24` 주석이
extra 로 뒀다가 `uv sync` 가 pytest·ruff 를 지워버린 사고를 기록해두었다.

## 12. 테스트 — 무엇이 규칙이 되는가

`tests/test_web.py` 의 컴플라이언스 회귀 테스트가 절대 규칙 5 자체인 것처럼, 아래가 이 문서의
규칙 자체다.

- **비로그인으로 캠프 화면 요청 → `/login` 리다이렉트.** 라우트를 전수 순회해서 검사한다.
  새 라우트를 추가하고 보호를 잊으면 이 테스트가 잡는다.
- **캠프 A 세션으로 캠프 B 관할 요청 → 거부.** P-001 §10 격리 테스트의 웹 계층 짝.
- **미승인 계정 → `/pending` 외 전부 차단.** 공용 데이터 포함.
- **온보딩 미완료 → 데이터 화면 차단.**
- **인증 비활성 + `0.0.0.0` 바인딩 → 기동 거부.**
- **`_output.html` 을 verdict 없이 호출 → 실패.**
- **`test_serving_never_writes` 가 수정 없이 통과한다.** §3 의 해법이 지켜졌다는 증거다.
  이 테스트를 고쳐야 통과한다면 설계가 틀린 것이다.

## 13. 롤아웃

| 단계 | 내용 | 상태 |
|---|---|---|
| 1 | `data/control.db` 스키마 + 계정·세션 모듈 (웹과 무관하게 단위 테스트) | ✅ |
| 2 | `votelink account create-operator` CLI — 첫 운영자를 만드는 유일한 경로 | ✅ |
| 3 | 미들웨어 + `/login`·`/logout` + `base.html` 로그인 상태 | ✅ |
| 4 | `/signup` → `/pending` + 운영자 승인 (승인 화면은 P-003, CLI 로 먼저 가능) | ✅ |
| 5 | `/onboarding` — P-001 §6 의 항목 + emd 검증 | ✅ |
| 6 | 라우트 스코프 집행 + §12 테스트 전부 | ✅ |
| 7 | `_output.html` 구멍 막기 + `DEFAULT_HOST` 정책 전환 | ✅ |

3~7 단계는 한 커밋이다. 미들웨어 없이 `/login` 만 있으면 아무것도 지켜지지 않고, 관할 집행
없이 `/onboarding` 만 있으면 캠프가 서로의 화면을 열 수 있다. **가운데서 멈출 수 있는 자리가
없어서** 쪼개지 않았다.

인증은 기본이 **꺼짐**이다(`WebSettings.auth`). 그 상태의 앱은 지금까지의 1인 로컬 사용과
정확히 같고, `cli.py` 가 그 앱을 `127.0.0.1` 밖으로 내보내지 않는다. 멀티캠프로 넘어가는
스위치가 `--auth` 하나다.

## 14. 제약과 위험

- **공유 계정 + 비밀번호만 = 비번 유출이 곧 캠프 공간 유출.** 2FA 를 두지 않기로 했으므로
  대응 수단은 운영자의 세션 강제 종료와 접속 기록뿐이다. 경쟁 캠프를 함께 받는 상황에서
  이것이 가장 큰 잔여 위험이다.
- **감사 로그가 "이 캠프의 누군가"까지만 말한다**(§7). 캠프 내부 행위자는 특정되지 않는다.
- **시스템은 `reviewed_by` 서명을 보증하지 않는다**(§7).
- **캠프는 자기 격리를 스스로 확인할 수단이 없다.** 감사 로그를 운영자만 열람하기로 했다(P-003).
  계약과 운영자의 감사 보고가 대신한다.
- **비밀번호 재설정에 메일 발송 인프라가 필요하다.** 이번 범위 밖이라 초기에는 운영자가
  임시 비밀번호를 발급한다. 캠프 수가 적을 때만 견딘다.
- **`data/control.db` 가 새로운 단일 장애점이자 유출 지점이다.** `raw/`·`records/` 와 달리
  재생성할 수 없다. 백업 정책이 필요하다.
- **세션 유휴 12시간은 근거가 약한 값이다.** 운영하며 조정한다.
